# Staffly — локальный запуск и хранилище

## Конфигурация

Запускайте команды из корня проекта. Нужны Node.js, npm и PostgreSQL.

1. `npm ci`
2. Скопируйте `src/server/.env.example` в `src/server/.env` и заполните настройки.
3. Установите права `chmod 600 src/server/.env`.
4. Выполните `npx prisma migrate deploy`.
5. Запустите `npm run dev:all`.

### Какие env-файлы используются

- `src/server/.env` — локальные серверные настройки. Их читают backend и Prisma CLI. Секреты не должны иметь префикс `VITE_`: такие переменные доступны браузеру.
- `src/server/.env.example` — безопасный образец для нового разработчика; хранится в Git.
- `src/server/.env.test` — отдельная БД `staffly_test` и тестовые ключи; создаётся командой `npm run test:setup`, не хранится в Git.
- `src/server/.env.legacy` — сохранённая старая конфигурация из корневого `.env`. Не загружается приложением. Её URL отличался от рабочего, поэтому файл сохранён для ручной проверки, без потери старых реквизитов.

Корневой `.env` для текущего frontend не нужен: запросы идут через `/api`, Vite проксирует их на порт 3001. `prisma7.config.ts` задаёт схему/миграции и выбирает серверный env; `PRISMA_ENV_FILE` позволяет явно выбрать тестовый файл. `vite.config.ts` нужен для frontend, `tsconfig*.json` — для разных целей TypeScript; это не дубли env.

`npm run start:server` запускает backend в production. Для развёртывания настройте реальный `APP_ORIGIN`, SMTP, отдельные секреты и абсолютный `LOCAL_STORAGE_ROOT` вне публичного каталога. Вместо локальных реквизитов можно передать переменные через окружение процесса. Backend и frontend требуют отдельной настройки сервера/HTTPS при развёртывании.

## Тесты

`npm run test:setup`, затем `npm test`.

Тесты требуют именно БД `staffly_test`; её содержимое очищается тестами. Каждый запуск получает свою временную папку в системном temp и удаляет её после завершения, включая неуспешный запуск. Пользовательская `storage` не используется. После аварийного завершения процесса (например, SIGKILL) системная временная папка может остаться; она не находится в проекте.

## Storage

`LOCAL_STORAGE_ROOT` по умолчанию — `./storage`, относительно рабочего каталога процесса.

- `users/<user UUID>/avatars/<file UUID>.webp` — обработанные аватарки.
- `organizations/<organization UUID>/logos/<file UUID>.webp` — обработанные логотипы.
- `organizations/<organization UUID>/requests/<request UUID>/<file UUID>.<pdf|jpg|png|webp>` — вложения заявок, с проверкой типа содержимого. UUID — внутренние ключи, исходные имена хранятся только для отображения/скачивания.
- `<object key>.<UUID>.tmp` — незавершённая атомарная запись.
- `.DS_Store` — метаданные macOS Finder.

Изображения профиля/организации конвертируются в WebP; вложения сохраняют свой проверенный формат. Старые тесты записывали файлы в пользовательскую папку: среди остатков есть белые JPEG 8×8 и неполноценные PDF-заглушки. Тестовая БД очищалась, файлы оставались. Эти старые файлы не удаляются автоматически.

Перед записью файла создаётся запись намерения загрузки в `stored_files` с часовым сроком. Привязка к профилю/организации/заявке и снятие отметки удаления происходят одной транзакцией. При ошибке запись остаётся для повторной очистки; после падения процесса незавершённую загрузку удалит существующий worker. Активные загрузки не очищаются до истечения срока. Очередь удаления обрабатывается при старте сервера и каждые 10 минут; временные файлы удаляются только для ключа, явно находящегося в очереди. Пустые директории также удаляются.

Права: каталоги 0700, файлы 0600. Storage keys проверяются, обход через `..`, абсолютные пути и символические ссылки внутри хранилища запрещён. Не предоставляйте сторонним процессам право записи в хранилище. Вложения выдаются через API с проверкой доступа; хранилище нельзя публиковать как static directory.

### Аудит и безопасная очистка

`npm run storage:audit` — только чтение: количество зарегистрированных файлов, отсутствующих, не зарегистрированных в текущей БД, совпадающих с тестовыми заглушками, временных и небезопасных записей; проверка размеров/SHA-256. Содержимое и секреты не выводятся.

`npm run storage:audit -- --cleanup` — обработка только существующих, уже наступивших записей очереди удаления в текущей БД. Незарегистрированные файлы сохраняются: они могут принадлежать другой БД или резервной копии. Не удаляйте их только потому, что они отсутствуют в одной БД. Аудит не является полной проверкой структуры PDF или антивирусом.
