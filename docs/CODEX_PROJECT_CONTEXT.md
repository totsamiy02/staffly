## Что это за продукт

**Staffly** — веб-сервис для управления небольшой командой и HR-процессами. Один пользователь может состоять в нескольких организациях, а данные и права привязаны к организации и её точкам. В организации обязательно есть хотя бы одна действующая точка с названием, городом, адресом и часовым поясом. Основные сценарии: регистрация и вход; создание организации и приглашение сотрудников; управление участниками и ролями; планирование и учёт смен, рабочего времени и отсутствий; подача и обработка заявок; хранение документов и подтверждение ознакомления; уведомления. Внешняя часть — публичный сайт и правовые страницы, рабочая часть начинается с `/app`.

Роли `OWNER | ADMIN | MEMBER` общие для организации в `OrganizationMember.role`. Администратор управляет только действующими точками, в которые назначен через `LocationMember`; назначения согласованы с общей ролью. Остальные точки доступны ему для просмотра с правами сотрудника. `getMembership` возвращает эффективную роль выбранной точки, исходную `organizationRole`, `readableLocationIds` и `managedLocationIds`. Роль меняет только владелец; изменение обновляет назначения во всех точках. Интерфейс показывает общую роль, окончательные права действий проверяет сервер по текущим назначениям.

## Стек и путь запроса

| Технология | Как применяется здесь |
| --- | --- |
| React 19 + TypeScript | Компоненты страниц и типы интерфейса в `src/`. |
| Vite 8 | Локальная сборка клиента; `/api` проксируется к Express на `localhost:3001` (`vite.config.ts`). |
| React Router 7 | Публичные и защищённые маршруты в `src/App.tsx`; вложенные страницы организации в `src/pages/app/organization-layout.tsx`. |
| TanStack Query 5 | Серверные данные, мутации, кеш и инвалидирование в `src/app/*/queries.ts`; общие настройки в `src/main.tsx`, обновление активных данных в `src/app/live-query.ts`. |
| SCSS / Sass | Глобальные стили `src/index.scss`, `src/styles/`; стили модулей рядом со страницами. |
| Node.js + Express 5 + TypeScript | API в `src/server/`; маршруты принимают запросы, сервисы выполняют бизнес-логику. |
| Zod | Валидация параметров, query и тела запросов в `src/server/**/schemas.ts` и отдельных маршрутах. |
| PostgreSQL + Prisma 7 + `pg` | Реляционные данные и транзакции; `prisma/schema.prisma`, миграции `prisma/migrations/`, клиент через `@prisma/adapter-pg` в `src/server/db.ts`. |
| JOSE + Argon2id | JOSE подписывает и проверяет короткоживущий access JWT; Argon2id хеширует пароли (`src/server/auth.ts`). |
| HttpOnly cookies + cookie-parser | Refresh-токен сеанса хранится в cookie; access JWT клиент держит в памяти и отправляет как Bearer-токен. |
| Helmet + express-rate-limit | Защитные HTTP-заголовки/CSP и ограничения частоты запросов в серверных маршрутах. |
| Nodemailer + Sharp | Отправка писем (`src/server/mail.ts`); обработка аватаров и логотипов перед сохранением (`src/server/storage/image-service.ts`). |

Обычный путь данных: **страница/компонент → hook из `src/app/.../queries.ts` → `useAuth().apiRequest()` → `/api` → `src/server/.../routes.ts` → сервис → Prisma/PostgreSQL**. После мутации обновляй связанные ключи TanStack Query, иначе соседние экраны могут показывать старые данные.

## Повторное использование по задачам

- **Новые страницы/элементы интерфейса:** сначала ищи готовые паттерны в `src/component/ui/`, `src/pages/app/app.scss` и соседнем модуле. `ToastProvider` / `useToast` дают обратную связь; `Avatar`, `Select`, кнопки и бейдж роли уже используются в рабочих страницах. Не считай все окна одним компонентом: есть общий `ui/modal`, модульный `DocumentDialog` и `AnimatedOverlay` для анимации модалок/панелей.
- **Новый запрос к API:** используй `useAuth().apiRequest()` и существующие query hooks. `auth-context.tsx` умеет повторить запрос после обновления access-токена; там же есть `uploadFile`, `previewFile`, `downloadFile`, `uploadImage`. Для живых данных сверяйся с `liveQueryOptions` и существующими ключами кеша.
- **Изменение логики организации:** проверяй `src/server/organizations/permissions.ts`, сервисы организации и членство. `getMembership` отсекает вышедших участников и удалённые организации; нельзя полагаться только на роль, пришедшую с клиента.
- **Изменение документов:** используй `src/app/documents/queries.ts`, `src/pages/app/documents/document-drawer.tsx` / `document-dialog.tsx`, `src/server/documents/{routes,service,schemas,file-validation}.ts`; учитывай область видимости, получателя, папки, редакции, удаление и статусы ознакомления.
- **Изменение уведомлений:** topbar находится в `src/pages/app/topbar/`, клиентские hooks — в `src/app/organizations/queries.ts`, серверная история и фильтрация — в `src/server/organizations/notification-service.ts`. На `/app` история общая по доступным организациям, внутри организации ограничена её `organizationId` и выбранной точкой; общие уведомления включаются в каждую точку. Ссылки на смены, заявки и документы содержат `location`, чтобы открыть правильную точку.

## Важные сценарии и серверные тонкости

1. **Авторизация.** `src/server/auth.ts` выдаёт access JWT примерно на 15 минут. Refresh-токен — случайный, в БД хранится его хеш; cookie имеет `HttpOnly`, `SameSite=Lax`, `Secure` в production и путь `/api/auth`. Refresh вращает токен, сервер проверяет действующий `AuthSession`. `src/app/auth/auth-context.tsx` хранит access-токен в памяти и очищает кеш Query при смене пользователя/выходе. Есть подтверждение email, восстановление пароля, управление сеансами; письма — `src/server/mail.ts`.
2. **Организации и приглашения.** Создание, участники, email/code приглашения, смена роли, передача владения и удаление разделены между `organizations/routes.ts`, `service.ts`, `invitation-service.ts`, `sensitive-action-service.ts`. Чувствительные действия требуют отдельного подтверждения. Проверяй граничные случаи OWNER/ADMIN/MEMBER и покинувшего организацию участника.
3. **Смены, отсутствие, статистика.** Роуты и сервисы в `src/server/schedule/`, время и часовой пояс — отдельные модули `timezone.ts`, `statistics.ts`, `planning.ts`, `workload.ts`. Есть история смен, плановые/фактические часы, отсутствия и связи с заявками. При изменении смен проверяй пересечения, часовой пояс точки, пересечения смен сотрудника во всей организации, уведомления и пересчёт статистики.
4. **Заявки.** Типы заявок настраиваются организацией; сотрудник создаёт/редактирует/отменяет свои, руководители рассматривают входящие. Решение может затрагивать смены/отсутствия, поэтому смотри `src/server/requests/shift-conflicts.ts`, `attachment-service.ts`, а также invalidation в `src/app/live-query.ts`.
5. **Документы.** Модели `DocumentFolder`, `Document`, `DocumentAcknowledgement` в Prisma. Документы бывают видимы организации или персонально сотруднику; есть назначение ознакомления, прогресс, подтверждение и сохранение истории. Файлы не публикуются как static: содержимое отдаёт авторизованный `POST .../content?action=preview|download` после проверки доступа. Успешная выдача файла отмечает открытие; простое открытие карточки — нет. Предпросмотр предусмотрен для PDF/изображений/текста, прочие форматы скачиваются. Проверяй MIME/размер и права и на списке, и на конкретном документе.
6. **Файлы и безопасность.** `src/server/storage/` отвечает за локальное закрытое хранилище, загрузки, обработку изображений и очередь очистки. Аватары/логотипы доступны через `/api/media/:fileId`, вложения заявок и документы — только через защищённые API. `src/server/index.ts` проверяет Origin мутаций и тип тела, ограничивает размер JSON; маршруты дополнительно валидируют данные Zod и ограничивают частоту. Не подключай `storage/` как публичную статику и не выводи секреты в клиентский `VITE_` env.

## Точки организации и права

- Модели: `OrganizationLocation`, `LocationMember`, `LocationTeam`, `LocationTeamMember`, `LocationTransfer`. Смены, заявки, шаблоны и приглашения имеют `locationId`; `Document` и `DocumentFolder` с `locationId = null` общие для организации. Составные внешние ключи с `organizationId` защищают от привязки данных к чужой организации.
- `src/server/organizations/location-context.ts`: middleware `selectLocation` в `index.ts` проверяет членство и `locationId` query / `x-staffly-location`, затем задаёт область запроса через `AsyncLocalStorage`. Без выбора берётся первая действующая точка. Для запросов к модулям используй `locationWhere` / `locationMemberWhere`, для прав — `getMembership`. Прямые внутренние вызовы сервисов без области сохраняют совместимость со старыми сценариями; HTTP-запросы к организации всегда проходят middleware.
- `location-service.ts`: создание/изменение/закрытие точек и назначения сотрудников. Владелец управляет всеми точками, назначает администраторов и меняет общие настройки. Администратор управляет сотрудниками, сменами, заявками и документами только назначенных точек. Состав и календарь всех действующих точек доступны всем участникам. Модели именованных команд остаются для совместимости и истории, их настройка убрана из интерфейса.
- Подмены встроены в заявки (`requests/service.ts`): `STAFFING` — потребность принимающей точки с датой, временем и должностью; `STAFFING_RESPONSE` — отклик сотрудника другой точки. Потребность видна в уведомлениях независимо от выбранной точки. Подтверждает **администратор принимающей точки** либо владелец; согласование исходной точки не требуется. Одной транзакцией создаются временный `LocationTransfer`, смена и решения по откликам, с проверкой отсутствий, нагрузки и пересечений во всей организации. Условия опубликованной потребности меняются через отмену и новую заявку. Прямой API постоянного перевода сохранён и требует владельца либо прав на обе точки; прежние смены не переписываются. Отсутствия общие для сотрудника: отмена пересекающихся смен требует прав на каждую затронутую точку.
- Расписание, заявки, статистика, шаблоны и месячная норма относятся к точке; должности и типы заявок общие, их настройки меняет владелец. Список сотрудников по умолчанию использует `directory=true`: все действующие сотрудники с назначением хотя бы в одну действующую точку. Есть фильтры поиска, роли, должности и `pointId`. `/all-members` / `useOrganizationDirectory` включает также неназначенных для распределения. Заявки поддерживают `pointId=all` либо конкретную точку; входящие/архив администратора ограничены управляемыми точками. Период учитывает даты отсутствия, время предложенной смены в часовом поясе точки либо дату создания обращения без периода.
- Документы отображают общие материалы и материалы всех назначенных точек независимо от выбранной среды. Просмотр календаря чужой точки не даёт доступа к её документам. Общими материалами управляет владелец, местными — назначенный администратор. Папки имеют `ORGANIZATION | ADMINS`; ограничение наследуется потомками и проверяется для списков, карточек, байтов, ознакомлений и уведомлений. `accessVisibility` в DTO отражает наследованный доступ, `visibility` — собственную настройку для редактирования. `pointId` позволяет менять область документа/папки; перемещение папки переносит вложенные материалы и отменяет незавершённые ознакомления потерявших доступ. Доступ отмечен иконками и названиями точек, фильтры — поиск, точка и сортировка; навигация папок имеет только возврат.
- Интерфейс: переключатель в `organization-layout.tsx` работает и при свёрнутом меню; настройка в `location-settings.tsx` на вкладке «Точки»; общие поля в `location-fields.tsx`. Создание требует `firstLocation` (по умолчанию «Основная точка») и поддерживает до 49 дополнительных `locations`, без настройки команд. Назначение сотрудников доступно в настройках и действиях строки сотрудника. Используются существующие `Select`, `DatePicker`, `TimeInput`, `EmployeePicker` с аватарами, `AnimatedOverlay`, `DocumentDialog` и бейджи ролей. Цвет точки из `locationTone` общий для сотрудников, документов и заявок.
- `locations/overview` возвращает сотрудников и смены сегодня для каждой точки в её часовом поясе. Главная показывает количество и модалку с людьми; ссылка открывает день календаря через `month` / `day`. Календарь показывает до пяти карточек в увеличенной плитке и число остальных; полный день доступен в панели.
- `useAuth()` добавляет выбранный `locationId` к API организации и операциям с файлами. Выбор хранится в URL `?location=` и `sessionStorage` отдельно для пользователя/организации. Ключи Query включают точку, модули пересоздаются при переключении, формы и прежние результаты не смешиваются. Для ссылок из общих разделов/уведомлений явно передавай точку ресурса.
- Миграция `20261002120000_organization_locations` создала для старых организаций «Основную точку» и перенесла текущие данные; старые документы остались общими. Миграции `20261003090000_location_workflows` и `20261003100000_location_closure_target` добавляют заявки подмен, доступ папок, общий `ADMIN` и ограничение цели кода закрытия. Неизвестные город/адрес заполняет владелец позже. Последнюю точку закрыть нельзя; остальные закрывает владелец одноразовым кодом из письма, привязанным к точке (`ARCHIVE_LOCATION`). Неверные попытки учитываются, код имеет срок и лимит попыток. Будущие смены, открытые заявки и незавершённые подмены сначала требуют обработки; история закрытой точки доступна владельцу.

## Запуск и проверки

- Локальная конфигурация: `src/server/.env` (секреты), образец `src/server/.env.example`; frontend обращается к относительному `/api`. Подробности — `README.md`. `src/server/.env.legacy` приложением не загружается.
- Из корня проекта: `npm run dev:all` (Vite + API), `npm run lint`, `npm run build`.
- Для тестов: `npm run test:setup`, затем `npm test`. **Тестовая БД `staffly_test` очищается**; `src/server/db.ts` запрещает тестовый режим на другой БД. Перед запуском тестов убедись, что подключение указывает на выделенную тестовую БД. Не запускай миграции/очистку на рабочей БД без понимания последствий.
- После изменения Prisma schema нужна миграция и генерация клиента (`prisma generate` выполняется в сценариях npm). При проверке новой функции выбирай подходящий модульный или интеграционный сценарий; для интерфейса дополнительно проходи основной путь пользователя и состояния загрузки, ошибки и пустого списка.
